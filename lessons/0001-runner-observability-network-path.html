Lesson 01 · Runner Observability

為什麼完整架設要經過這麼多關卡？

你看到的不是七個互不相關的設定，而是同一條「Runner 把進度送到 Monitor」的路徑， 每一關都在排除一種不同的故障。

一句話版本： 這套系統就是「地址簿 → 大門 → 保全 → 加密通道 → API 櫃台 → 應用程式資料」。 內部公司網路會讓範圍比較單純，但不會讓這些層次消失。

先看完整路徑

Runner要送出進度
名稱monitor-test.local
TCP8765 大門
TLS加密與身份
HTTPAPI 路徑
Token請求身份
Monitor儲存與投影

想像你要把一份文件送到公司另一棟大樓：先查地址，再走到大樓，再通過入口， 進入加密的櫃台通道，找到正確窗口，出示識別證，最後櫃台才會接收文件。 任何一步失敗，下一步都不會有意義。

每一層到底在確認什麼？

層次它要回答的問題你看到的測試通過代表什麼
Hostname / DNS 「monitor-test.local」是哪台電腦？ hosts 或 DNS lookup Runner 找到正確的 IP。這像查地址簿。
TCP 能不能連到 Monitor 的 8765 port？ Test-NetConnection 網路路徑、監聽狀態與防火牆至少允許這個連線。
Firewall 這個 port 是否被門禁擋住？ 通常由 TCP 失敗間接發現 Monitor 的入口允許 Runner 進入。TCP 失敗不一定只代表 Firewall，也可能是 IP 錯或服務沒啟動。
TLS / Certificate 通道是否加密？Runner 連到的真的是這個 Monitor 嗎？ Invoke-WebRequest https://... 資料不以明文傳送，且憑證名稱和信任鏈符合請求。
HTTP 你找的是不是正確的 API？ /api/health、/v1/events 應用程式確實有回應，不只是 port 開著。
Bearer token 這個呼叫者是否被允許送資料？ Canary Auth 錯 token 會被拒絕，正 token 可以恢復。
Event / liveness Monitor 能否正確判斷 online、offline、recovery？ Canary Smoke、OfflineRecovery 資料不只「送到」，還被正確投影成 dashboard 狀態。

把你剛剛遇到的錯誤串起來

第一個問題：TCP 根本沒有到正確的電腦

Runner 查到的 monitor-test.local 是舊位址 192.168.1.50， 但 Monitor 實際位址是 192.168.24.141。所以 Runner 很努力地連線， 只是連到錯的地址；這時候 Monitor 本機明明在 Listen，Runner 仍然會失敗。

修正 hosts mapping 後，TCP 成功。這代表「地址簿」與「大門」已經通了， 但還沒有證明 HTTPS、API 或 token 正常。

第二個問題：TCP 通了，但 HTTPS 不信任這個身份

你用 IP 呼叫 HTTPS。TLS 憑證通常會把允許的 hostname/IP 寫在 SAN 裡； 目前測試憑證是給 monitor-test.local 與原本的測試 IP， 不等於「任何 IP 都可以使用」。另外，self-signed 憑證也必須被 Runner 放進信任的憑證存放區。

所以「TCP 成功」和「HTTPS 成功」並不矛盾：前者只看大門能不能打開， 後者還要驗證通道和身份。改用憑證對應的 hostname，並讓 Runner 信任該憑證後， HTTPS health 才成功。

四個命令，各自只負責一件事

$monitorName = 'monitor-test.local'
$port = 8765

# 1. 名稱：查到哪個 IP
Resolve-DnsName $monitorName

# 2. TCP：8765 大門是否打得開
Test-NetConnection -ComputerName $monitorName -Port $port -InformationLevel Detailed

# 3. HTTPS + HTTP：服務是否真的回應 health
Invoke-WebRequest -UseBasicParsing -Uri ("https://{0}:{1}/api/health" -f $monitorName, $port)

# 4. 應用程式：送事件、驗證 dashboard 與 liveness
.\scripts\Invoke-RunnerCanary.ps1 -Mode Smoke -Endpoint ("https://{0}:{1}" -f $monitorName, $port) -RunnerId '00000000-0000-0000-0000-000000000006' -TokenPath 'C:\runner-observability-secrets\monitor-token.txt'
注意： Test-NetConnection 成功不代表 TLS 憑證正確； /api/health 成功也不代表 bearer token、事件序號與 offline/recovery 狀態全部正確。這正是為什麼還需要 Canary。

為什麼 OfflineRecovery 要等很久？

它不是卡住，而是在刻意模擬「Runner 停止送 heartbeat」： 先送一個正常 heartbeat，等超過 liveness timeout，再確認 dashboard 變成 offline 且原因是 heartbeat_timeout，最後再送一個較新的 heartbeat，確認狀態可以恢復 online。預設等待約 601 秒，是為了越過 600 秒的 offline 判定門檻。

Dashboard 要在哪裡開？

PowerShell 視窗只是「啟動 Monitor 的地方」，不是 dashboard 的畫面。 Dashboard 是 Monitor 提供的網站首頁，根路徑是 /。請在 Monitor Host 或 Runner 上開瀏覽器，輸入： 

https://monitor-test.local:8765/
請使用 hostname，不要優先使用 IP。 你的測試憑證是簽給 monitor-test.local 的；用 https://192.168.24.141:8765/ 時，瀏覽器會把「網址中的 IP」 和「憑證中的身份」拿來比對，兩者不一致就可能顯示不安全。

如果瀏覽器仍然顯示「不安全」

  1. 先確認網址是 https://monitor-test.local:8765/，不是 IP。
  2. 確認「正在開瀏覽器的這台電腦」也能解析 hostname；hosts 修改只對修改過的電腦有效。
  3. 若使用 self-signed 測試憑證，將公開憑證匯入目前使用者的 Trusted Root store：
Import-Certificate -FilePath 'C:\runner-observability-secrets\monitor.crt' -CertStoreLocation 'Cert:\CurrentUser\Root'

若要讓這台電腦的所有使用者都信任，才使用 Cert:\LocalMachine\Root，並以系統管理員 PowerShell 執行。 只匯入 .crt 公開憑證，不要把 .key 複製到 Runner 或匯入瀏覽器。

測試環境可以在瀏覽器的進階畫面暫時選擇繼續，但那只是繞過警告； 正確的驗證方式仍是使用對的 hostname 並建立信任。不要把 -SkipCertificateCheck 當成正式設定。

用 PowerShell 確認 dashboard API

首頁會由 JavaScript 自動呼叫 /api/dashboard。因此可以把問題拆成 「網站首頁」和「dashboard JSON」兩步： 

Invoke-WebRequest -UseBasicParsing -Uri 'https://monitor-test.local:8765/api/dashboard'

這個 endpoint 目前是 monitor 的 dashboard 讀取介面，不需要把 bearer token 放進瀏覽器網址；token 只用於 Runner 對 /v1/events 的送資料請求。

最實用的故障判斷表

現象先想哪一層？下一步
hostname 找不到 名稱 / hosts / DNS Resolve-DnsName，確認 mapping 是否指向目前 Monitor IP。
TCP False IP、路由、Firewall、Listen 在 Monitor 看 Get-NetTCPConnection -LocalPort 8765，再核對 Runner 查到的 IP。
TCP True，但 SSL trust 失敗 TLS 名稱或憑證信任 用憑證中的 hostname；確認 Runner 已信任測試憑證。
HTTPS health 成功，但 Canary Auth 失敗 token / API auth 確認 token 檔案沒有多餘空白，且 Monitor 啟動時使用相同 token。
Smoke 成功，但 OfflineRecovery 未完成 這通常是等待中的正常狀態 不要重跑或送額外 heartbeat；等 timeout 與 recovery 階段結束。
PowerShell health 成功，但瀏覽器顯示不安全 瀏覽器使用的 hostname、憑證信任或快取 改用 monitor-test.local，確認瀏覽器所在電腦已匯入公開憑證。
首頁開得起來，但沒有 Runner 資料 Monitor 收到的事件或 dashboard API 重新整理頁面，再查 /api/dashboard；不要只看 port 是否開啟。

小測驗：先猜，再看答案

1. TCP 是 True，HTTPS 卻出現 SSL trust error，哪一層還沒通？

答案：A。TCP 只證明可以碰到 port；TLS 還要驗證加密通道和伺服器身份。

2. hostname 指向舊 IP，但 Monitor 在新 IP 上 Listen，最可能發生什麼？

答案：A。token 在應用程式層，無法修正名稱解析或路由。

3. OfflineRecovery 等待中，應該先做什麼？

答案：A。額外 heartbeat 會打斷「模擬離線」的條件。
