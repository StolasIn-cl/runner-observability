Runner Observability · Quick reference

網路排查速查表

由外而內：先確認「找得到」，再確認「連得到」，最後確認「服務真的懂你的資料」。

最短判斷法： Test-NetConnection 通過，只代表 TCP 大門打得開；還要用 Invoke-WebRequest /api/health 驗證 HTTPS/HTTP，最後才用 Canary 驗證 token、事件與 liveness。
層它在問什麼？命令失敗時先看什麼？
名稱 這個名稱指向哪台電腦？ Resolve-DnsName monitor-test.local hosts/DNS 是否仍指向舊 IP。
TCP Runner 能否打開 Monitor 的 8765 大門？ Test-NetConnection monitor-test.local -Port 8765 目標 IP、服務是否 listen、Windows Firewall、路由。
TLS 這條 HTTPS 通道是否加密，且對方身份可信？ Invoke-WebRequest https://monitor-test.local:8765/api/health 憑證 SAN 是否含 hostname、Runner 是否信任憑證。
HTTP API 路徑是否正確，服務是否有回應？ /api/health、/api/dashboard URL、port、scheme、服務 log。
Auth 這個 Runner 是否持有正確 token？ Invoke-RunnerCanary.ps1 -Mode Auth token 檔案內容、Bearer header、服務啟動參數。
資料與 liveness 事件是否被接收、投影，且離線後能恢復？ Smoke、OfflineRecovery RunnerId、序號/epoch、timeout、database 與 dashboard。

建議順序

  1. 在 Monitor 確認 0.0.0.0:8765 正在 Listen。
  2. 在 Runner 確認 hostname 解析到目前 Monitor IP。
  3. 在 Runner 執行 TCP 測試。
  4. 使用 hostname（不要先改成 IP）執行 HTTPS health。
  5. 在瀏覽器開啟 https://monitor-test.local:8765/ 查看 dashboard。
  6. 最後才跑 Smoke、Auth、OfflineRecovery、NetworkFailure。
本次案例：名稱曾指向 192.168.1.50，但 Monitor 實際位址是 192.168.24.141；修正 mapping 後 TCP 通過。接著使用 IP 做 HTTPS 時， 憑證名稱/信任不一致；改用憑證中的 hostname 並讓 Runner 信任憑證後，HTTPS 也通過。
瀏覽器顯示「不安全」：先改用 https://monitor-test.local:8765/，再確認瀏覽器所在電腦信任 monitor.crt。使用 IP、未信任 self-signed 憑證，或 hostname 不在 憑證 SAN 中，都可能觸發瀏覽器警告。

這張速查表只包含診斷方向，不包含任何 token、private key 或憑證內容。
